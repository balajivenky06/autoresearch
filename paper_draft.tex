\begin{abstract}
\textbf{Context.} Retrieval-augmented generation (RAG) is
widely assumed to improve LLM-generated unit tests, but evaluations
rely on surface metrics and single models, leaving defect-detection
capability untested. \textbf{Objective.} We quantify whether
retrieval augmentation improves the \emph{defect-detection} capability
of generated tests, and whether any such effect transfers across
LLMs. \textbf{Method.} We ran a $4 \times 4$ factorial experiment---
four generation methods (Plain LLM, Random RAG, Simple RAG, Iterative
Critique) by four open-weight LLMs (3B--30B parameters)---over 100
HumanEval and MBPP functions, yielding 1{,}443 valid observations and
9{,}660 mutants, analysed with Type-III ANOVA and mixed-effects
regression. We added a three-annotator blinded human evaluation and a
Pynguin baseline matched on the same functions. \textbf{Results.}
Method choice has no detectable effect: the spread across all four
methods is 0.011 in mean kill rate against 0.232 across models
($21.7\times$), and no pair separates in any scope. Semantic retrieval
beats a random-chunk placebo by 0.3 percentage points. An apparent
faithfulness--kill-rate correlation ($r = -0.907$) vanishes once model
is controlled ($r = +0.079$). Annotators ranked Iterative Critique
highest on all three rubric dimensions, significantly so on two once
model and annotator are controlled for, yet ratings do not predict
kill rate ($r = +0.18$, $p = 0.30$). \textbf{Conclusion.} Model
selection, not retrieval design, determines defect detection, and
human-perceived quality is a separate construct from it.
\end{abstract}

\begin{highlightslist}
\item RAG method choice has no effect on mutation kill rate across four LLMs
\item Model choice moves defect detection 21.7x further than method choice
\item Semantic retrieval beats a random-chunk placebo by 0.3 percentage points
\item A faithfulness-kill-rate correlation of -0.91 is a model confound
\item Annotators prefer tests whose defect detection is no better
\end{highlightslist}

\section{Introduction}\label{sec:introduction}
Automated unit-test generation has been a target of empirical
software-engineering research for decades, motivated by the
well-documented cost of manual test authoring and the high marginal
value of each additional test \citep{daka2014,almasi2017}. The
dominant paradigm prior to 2022 was \emph{search-based software
testing} (SBST): tools like EvoSuite for Java and Pynguin for Python
treat test-suite synthesis as an optimization problem, evolving a
population of candidate test cases against a coverage- or
mutation-based fitness function \citep{fraser2011,lukasczyk2022}.
These tools achieve high branch coverage on self-contained functions
and have demonstrated practical value in industrial deployments, but
they suffer from two well-known limitations: the
\emph{regression oracle problem} (their assertions encode observed
return values, not specifications) and a \emph{per-function
search-budget cost} that scales poorly to large codebases. The
arrival of large language models capable of synthesizing readable
test code has shifted this landscape. LLMs trained on public source
code can produce pytest- or JUnit-formatted test suites that read
like hand-written tests, encode specifications drawn from docstrings
or function signatures, and require no per-function search budget
beyond inference time \citep{schafer2024,tufano2022}. Multiple recent studies have benchmarked
LLM-generated tests against search-based baselines and reported
competitive or superior effectiveness on standard benchmarks
\citep{schafer2024,lemieux2023codamosa,dakhel2024mutation,
straubinger2025debug,konstantinou2026newer}. The question that frames the present paper is no
longer ``can LLM replace SBST?''—the empirical answer to that is
``yes, on coverage metrics''—but rather: \emph{once we accept
LLM-based test generation, which augmentation methodology produces
the best tests, on which kinds of code, with which underlying LLM?}

\subsection{The retrieval-augmentation question}\label{sec:intro-rag}
A natural augmentation for LLM test generators is
\emph{retrieval-augmented generation} (RAG). The original RAG
framework \citep{lewis2020} augments an LLM's prompt with passages
retrieved from a knowledge base; in the test-generation context, the
knowledge base is typically a curated set of testing tutorials,
framework documentation, and example test suites. The general framework is surveyed by
\citet{rag4code2025}. Several variants have been applied to code
tasks, and they differ in what they retrieve and how often:

\begin{itemize}
\item \emph{Simple RAG} performs a single top-$k$ retrieval pass and
  prepends the result. Its strength is that it is cheap---one
  embedding lookup---and its weakness is that the retrieval is blind
  to what the model subsequently does with it.
\item \emph{Iterative-Critique RAG} drafts, then critiques and
  refines across several rounds. It can repair an unusable first
  draft, at a cost of several extra inference calls per function; the
  known risk is that a critique loop drifts toward over-specific
  assertions that do not hold.
\item \emph{Random RAG} is not a technique but an \emph{ablation}:
  chunks are drawn at random from the same corpus, so the contrast
  against Simple RAG isolates the contribution of retrieval
  \emph{relevance} from that of simply having more context in the
  prompt. Studies that omit this arm cannot separate the two.
\end{itemize}

\noindent Retrieval has been evaluated on adjacent code tasks such as
repository-level completion \citep{zhang2023repocoder} and
retrieval-augmented code generation \citep{su2025evor,lu2022reacc}.
For \emph{unit test generation specifically} the literature is
thinner: \citet{shin2026ragtest} and \citet{zhang2026refrag} are the
two closest studies, and neither measures defect detection
(\S\ref{sec:related-rag}). That leaves three methodological gaps,
which we address in this paper.

\subsection{Three gaps in existing work}\label{sec:intro-gaps}

\paragraph{Gap 1: Surface-level evaluation metrics.}
Most LLM-test-generation studies report syntactic-validity rates,
BLEU or ROUGE similarity to ground-truth tests, embedding-based
semantic similarity, or edge-case-coverage proxies. These are useful
for distinguishing working LLM pipelines from broken ones, but they
do not answer the question that matters for downstream deployment:
\emph{do the generated tests catch bugs?} A test suite with high
BLEU similarity to a ground-truth reference can have zero
defect-detection capability if it asserts only structural properties
(return type, list length) rather than specific oracle values. The
SE-relevant operationalization of ``do the tests catch bugs?'' is
\emph{the mutation kill rate}—the fraction of
systematically-injected code defects that the test suite detects
\citep{andrews2005,just2014}. Mutation testing has been a
gold-standard metric in the SBST literature for two decades but has
been used only sporadically in LLM-test-generation evaluations.

\paragraph{Gap 2: Single-LLM studies.}
The bulk of recent LLM test generation work evaluates a single LLM
(typically a frontier closed-weight model like GPT-4) and reports
the best RAG variant under that LLM. This methodology answers
``which RAG variant is best?'' but not ``which RAG variant is best
\emph{conditional on the underlying LLM}?''. As we demonstrate in
\S\ref{sec:results-generalisability}, the answer to the conditional
question is non-trivial: \emph{method rankings do not generalize
across LLMs}. Iterative-Critique RAG wins on three of the four
open-weight LLMs we test (llama3.2 3B, phi4 14B, qwen3-coder 30B-MoE)
but loses to Simple RAG on the strongest dense model in our pool
(qwen3.5 9B). A study that evaluated only on qwen3.5 would draw the
opposite conclusion from a study that evaluated only on phi4, and
neither study would surface the underlying interaction effect.

\paragraph{Gap 3: Limited connection to developer outcomes.}
Even where mutation-based metrics are reported, two further
evaluation components are typically absent. First, \emph{human
ratings of the generated tests}—does a developer reading the
generated suite see tests they would actually use? Without this
signal, automated quality metrics may diverge silently from
developer-perceived quality (we observe exactly this in
\S\ref{sec:results-humaneval}, where one LLM scores high on mutation
kill rate but low on human ratings). Second, \emph{a head-to-head
comparison against an established baseline tool}—
typically search-based test generation, the prior dominant paradigm. Without
such a baseline, claims about LLM-method ranking are difficult to
interpret. The present paper closes all three gaps: it uses
mutation-kill rate as the primary metric, conducts a three-annotator
human evaluation, and benchmarks against the Pynguin search-based
test generator on matched functions.

\subsection{Research objectives}\label{sec:intro-objectives}

The overall aim of this study is to determine \emph{whether
retrieval augmentation improves the defect-detection capability of
LLM-generated unit tests, and whether any such improvement transfers
across language models.} We pursue that aim through four specific
objectives:

\begin{description}
\item[\textbf{O1}.] To \emph{quantify} the effect of retrieval
  augmentation on mutation kill rate relative to unaugmented
  prompting, and to bound that effect with a stated level of
  statistical power rather than reporting significance alone.
\item[\textbf{O2}.] To \emph{separate} the contribution of retrieval
  \emph{relevance} from the contribution of additional prompt
  context, by including a random-retrieval condition identical to
  semantic retrieval in every respect except ranking.
\item[\textbf{O3}.] To \emph{test the transferability} of any method
  ordering across language models of differing capability, and to
  establish whether conclusions drawn on one model may be
  generalised to others.
\item[\textbf{O4}.] To \emph{compare} mutation-based defect detection
  against two independent quality signals measured on the same
  generated suites---blinded human ratings and a search-based
  generator baseline---and to determine whether the three signals
  agree.
\end{description}

\noindent Objectives O1--O4 map onto the research questions below as
O1\,$\rightarrow$\,RQ1--RQ2, O2\,$\rightarrow$\,RQ1,
O3\,$\rightarrow$\,RQ3--RQ4 and O4\,$\rightarrow$\,RQ5--RQ6.

\subsection{Research questions}\label{sec:intro-rqs}

The present paper addresses six research questions, organized
around the three gaps identified above:

\begin{description}
\item[\textbf{RQ1}.] Does retrieval-augmented LLM test generation
  produce tests with higher mutation kill rate than plain
  (un-augmented) LLM generation, across four open-weight LLMs
  spanning 3B--30B parameters?
\item[\textbf{RQ2}.] Is the method effect on mutation kill rate
  \emph{statistically significant} after controlling for
  source-sample difficulty and LLM choice, and does it concentrate
  on specific mutation operators or source benchmarks?
\item[\textbf{RQ3}.] Do \emph{method rankings generalize across
  LLMs}, or does the best method depend on the underlying LLM's
  capability tier?
\item[\textbf{RQ4}.] Does the \emph{token-overlap faithfulness}
  between generated tests and retrieved documentation predict
  mutation kill rate? Does \emph{semantic faithfulness} (an
  LLM-judge metric) predict it differently?
\item[\textbf{RQ5}.] Do \emph{human annotators} rank the four
  generation methods differently on test idiom quality, correctness
  and completeness---and does their ranking agree with the
  mutation-testing ranking of the same suites?
\item[\textbf{RQ6}.] How do LLM-based test generators \emph{compare
  against search-based test generation} (Pynguin) on the same
  matched functions, under a fixed search budget?
\end{description}

\subsection{Contributions}\label{sec:intro-contrib}

This paper makes five contributions to the empirical literature on
LLM-based unit-test generation:

\begin{enumerate}
\item \textbf{A cross-LLM mutation-testing study} of
  plain-vs-RAG test generation, with a random-retrieval control. We evaluate four methods (Plain LLM,
  Random RAG, Simple RAG, Iterative Critique) across four
  open-weight LLMs spanning 3B--30B parameters and dense vs
  mixture-of-experts architectures, on a 100-function subset of HumanEval + MBPP. To our knowledge, no prior study has reported
  this 4$\times$4 mutation-testing matrix at this sample scale.

\item \textbf{Statistically rigorous analysis} using Type-III ANOVA
  on the per-sample data, mixed-effects regression with
  \texttt{sample\_idx} as a random intercept, Tukey HSD post-hoc
  comparisons, and per-operator and per-benchmark decompositions.
  \emph{We report a well-powered null:} no method pair separates in
  any scope---pooled, per-benchmark, or per-operator---while the
  model factor is overwhelming ($F = 108.5$, $p < 10^{-60}$). We
  additionally report a decontaminated replication that rules out
  benchmark memorisation as the source of the null
  (\S\ref{sec:results-contamination}), a matched-subset replication
  controlling for differential test-filter attrition
  (\S\ref{sec:results-attrition}), and a power analysis bounding the
  effect we could have missed to roughly three percentage points
  (\S\ref{sec:limitations-conclusion}).

\item \textbf{A multi-annotator human evaluation reporting formal
  agreement statistics.} To our knowledge this is the first human
  evaluation of \emph{RAG-based} test generation to report
  inter-rater agreement rather than pooled means alone. Three
  independent annotators rated 40 stratified
  (function, generated\_tests) pairs blinded to method and model.
    \emph{Iterative Critique RAG ranked highest on all three rubric
  dimensions} (test idiom quality, correctness, completeness),
  significantly on two of them under a mixed-effects model
  controlling for model choice and annotator. This
  \emph{contradicts} the mutation-testing result rather than
  replicating it, and the two
  signals are uncorrelated at the suite level ($r = +0.18$,
  $p = 0.30$)---evidence that human-perceived test quality and
  defect-detection capability are separate constructs, and that
  studies reporting only one of them are not interchangeable.

\item \textbf{A per-operator LLM-vs-SBST comparison on matched
  Python functions.} Head-to-head LLM-vs-Pynguin comparison on
  mutation score is not itself new---\citet{dakhel2024mutation} and
  \citet{straubinger2025debug} both report one. What we add is the
  operator-level decomposition on a matched function set, which
  turns ``which paradigm is better'' into ``which defect families
  does each catch''. We benchmark our LLM methods against
  Pynguin 0.45.0 on the same 40 functions used in the human
  evaluation, with a 60-second per-function search budget. Matched on
  the 34 functions Pynguin could handle, LLM methods outperform it
  overall ($0.898$--$0.922$ vs $0.787$, Mann--Whitney $p < 0.001$),
  but the advantage is confined to the relational and boundary
  operator families (comparison $0.917$ vs $0.250$; boundary $0.817$
  vs $0.554$); on arithmetic and negate-boolean operators Pynguin
  \emph{leads} every LLM method ($0.850$ vs $0.809$ and $1.000$ vs
  $0.917$). The two approaches are therefore
  complementary along a specific axis---value-sensitive versus
  relational operator families---which is a sharper design brief for
  a hybrid generator than general complementarity.

\item \textbf{A methodological caution} about RAG retrieval
  quality: \emph{token-overlap faithfulness is a property of the
  model, not of the retrieval method} ($R^2 = 0.889$ by model
  against $0.118$ by method, $p = 0.605$). Pooled across the 11 RAG
  cells it correlates with mutation kill rate at $r = -0.907$
  ($p < 0.001$), which reads as a strong finding and is not one: the
  partial correlation controlling for model is $r = +0.079$
  ($p = 0.818$) and the within-model correlations are positive. In a
  cross-model design where one factor explains almost all outcome
  variance, any covariate tracking that factor will correlate with
  the outcome; we recommend reporting the partial correlation
  alongside the pooled one as a matter of course.
\end{enumerate}

A sixth methodological contribution: we release a
\emph{replication package} that includes the experimental sweep
TSV, the 40-pair human-evaluation worksheet (blinded), the three
annotators' ratings, the Pynguin runner, the analysis scripts, and
the Streamlit annotation application, which any group can fork to
run an analogous study on their own corpus.

\section{Related Work}\label{sec:related}
Our work intersects four literatures: LLM-based test generation,
retrieval-augmented generation for code tasks, mutation-testing-based
evaluation, and search-based software testing. We summarize each in
turn and position our contribution at the intersection.

\subsection{LLM-based unit-test generation}\label{sec:related-llmtg}
The use of large language models for unit-test synthesis predates
the modern transformer-LLM era. \citet{watson2020} showed that
sequence-to-sequence models could learn to generate assert
statements from method bodies, evaluated against Java open-source
projects. \citet{tufano2022assert} scaled this approach with a BART-based
encoder-decoder for assert generation, reporting improved accuracy
over prior sequence models; the training data came from
\citet{tufano2022}'s Methods2Test, a corpus of focal methods mapped
to their test cases, which is a dataset contribution rather than a
model.

The arrival of decoder-only frontier LLMs (Codex, GPT-3.5, GPT-4)
shifted research toward prompt-based test generation.
\citet{lemieux2023codamosa} combined LLM prompting with
search-based fallbacks, using the LLM to escape coverage plateaus
where pure SBST runs got stuck. \citet{schafer2024} introduced an adaptive generation loop in which the LLM iteratively refines its tests against runtime feedback, and provides the largest empirical comparison of frontier-LLM
test-generation pipelines to date, covering coverage, fault
detection, and runnable-test percentages across multiple LLMs and
benchmarks.

Several recent papers focus on specific LLM-test
generation pipeline choices. \citet{konstantinou2026newer} replicate
four such pipelines---HITS, SymPrompt, TestSpark and CoverUp---on
393 Java classes using current models, and find that a plain
zero-shot prompt outperforms all four on line coverage, branch
coverage and mutation score, at comparable query cost.
\citet{schafer2024} evaluate TestPilot across three LLMs of
differing capability and report that effectiveness tracks model
size and training corpus. 
\citet{siddiq2024junit} evaluates the quality of code (including
tests) generated by open-source code LLMs across multiple metrics.
\citet{wang2025llm4se} provides a recent survey of
LLM-for-software-testing work, mapping the rapid growth in this
area from 2023 to 2025 and identifying open research directions
that align with the gaps we address.

\paragraph{What these studies share.}
Each evaluates coverage, syntactic validity, semantic-similarity
(often BLEU or embedding-based), or runnable-test percentage.

\paragraph{What they do not do.}
None of these studies use mutation-based defect-detection as their
primary metric; none evaluate the same RAG variant across three or
more LLMs to surface interaction effects, and few include a
human-evaluation component that operationalizes
``developer-perceived quality'' alongside the automated metrics.
The present paper addresses all three gaps.

\subsection{Retrieval-augmented generation for code}\label{sec:related-rag}

Two recent studies apply retrieval directly to test generation.
\citet{shin2026ragtest} compare basic-instruction prompting against
two RAG configurations over three knowledge sources (API
documentation, GitHub issues, Stack Overflow) for five Python ML
libraries across four LLMs, and report that retrieval does not
improve correctness while adding 6.5\% line coverage on average.
\citet{zhang2026refrag} take a different route: rather than
retrieving documentation, their RefTest retrieves the \emph{existing
tests of related methods}, decomposing the retrieval target along
the Given--When--Then structure of a unit test, and report gains in
correctness, completeness and maintainability over ChatUniTest,
TestPilot, default-RAG prompting and EvoSuite on 1{,}515 Java
methods. The two results bound the question our study sits inside:
generic document retrieval appears to add little, while
task-specific structural retrieval appears to add a great deal. Our
knowledge base is of the first kind, and our null should be read as
evidence about that kind.

The original RAG framework \citep{lewis2020} demonstrated that
augmenting a sequence-generation LLM with a passage-retrieval step
produces better outputs on knowledge-intensive NLP tasks. The
framework has since been adapted to many code-generation contexts.
\citet{parvez2021} showed that retrieval-augmented code summarization
and generation could improve both code-completion and
natural-language-to-code translation. \citet{lu2022reacc}
demonstrated a retrieval-augmented code-completion framework using
both lexical and semantic retrieval. \citet{zhang2023repocoder}
introduced iterative retrieval at the repository level, where
retrieval is re-run after each draft refinement
—conceptually similar to our Iterative Critique baseline, though they evaluated
on code completion rather than test generation.

More recent work has explored variants of RAG specifically for code.
\citet{su2025evor} introduces an evolving retrieval store that grows
as code is generated, allowing later retrievals to benefit from
earlier generations' decisions. \citet{liu2025codereview} reports a
head-to-head comparison of multiple RAG variants on code-completion
benchmarks, finding that the best variant depends on the
type of code-completion task.

\paragraph{For RAG specifically applied to test generation,} the
literature is thin but no longer empty, and two 2026 studies bound
the question this paper sits inside. \citet{shin2026ragtest} compare
basic-instruction prompting against two RAG configurations over three
knowledge sources for five Python ML libraries across four LLMs, and
find that retrieval does not improve correctness while adding 6.5\%
line coverage. \citet{zhang2026refrag} retrieve the existing tests of
related methods rather than documentation, decomposing the retrieval
target along the Given--When--Then structure of a unit test, and
report gains in correctness, completeness and maintainability over
ChatUniTest, TestPilot, default-RAG prompting and EvoSuite on 1{,}515
Java methods. Neither evaluates defect detection. We are not aware of
a study that reports a cross-method, cross-LLM \emph{mutation-testing}
matrix for retrieval-augmented test generation, which is the gap this
paper addresses.

\paragraph{Where our faithfulness result sits.}
Our finding (\S\ref{sec:results-faithfulness}) that token-overlap
faithfulness is a model-level trait, and that its apparent
association with kill rate is confounded by model, connects to a
broader literature on \emph{retrieval faithfulness} in NLP.
\citet{maynez2020} and \citet{es2024ragas} propose faithfulness
metrics for retrieval-augmented generation and discuss the gap
between \emph{lexical} and \emph{semantic} faithfulness. Our
result is consistent with their observation that lexical alignment
with retrieved context is not equivalent to beneficial retrieval
use---in our data lexical faithfulness carries no information about
defect detection once model capability is held fixed---and it adds a
cautionary note specific to cross-model designs: where one factor
dominates the outcome, a cell-level faithfulness correlation will
reproduce that factor rather than measure retrieval quality.

\subsection{Mutation-testing-based evaluation}\label{sec:related-mutation}

Mutation testing has recently become the preferred effectiveness
metric for LLM-generated tests, and the dominant use is
\emph{generative} rather than evaluative: surviving mutants are fed
back into the prompt to drive better tests.
\citet{dakhel2024mutation} introduced this pattern with MuTAP,
augmenting prompts with surviving mutants on Python benchmarks and
reporting a 93.57\% mutation score against Pynguin and zero/few-shot
baselines. \citet{wang2026mutgen} extend it with an iterative
convergence mechanism on Java, \citet{bouafif2025primg} add a
learned mutant-prioritisation module for Solidity, and
\citet{straubinger2025debug} replace the feedback loop with
simulated scientific debugging, in which the model forms and tests
hypotheses about how to kill a specific mutant. At industrial scale,
\citet{foster2025ach} report Meta's ACH system generating
privacy-hardening tests from LLM-produced mutants across 10{,}795
Kotlin classes. A complementary line asks how good LLM-generated
\emph{mutants} are: \citet{wang2026mutationstudy} evaluate this on
851 real Java bugs and find LLM-generated mutants achieve 77.4\%
real-bug detection against 41.6\% for rule-based operators.

Our use of mutation testing is evaluative, not generative. No
surviving mutant ever enters a prompt in our pipeline; the mutation
analysis runs strictly downstream of generation, which is what makes
the kill rate an unbiased comparison across methods that never saw
it. We use rule-based AST operators rather than LLM-generated
mutants for the same reason---\citet{wang2026mutationstudy} show the
latter are more realistic, but they would introduce a second
model-dependent factor into a design whose purpose is to isolate
the first.

Mutation testing was introduced by \citet{demillo1978} as a thought
experiment about test-adequacy and was operationalized over the
next 30 years into a workable empirical methodology. The
foundational empirical justification—that mutation score
correlates with real fault detection capability—came from
\citet{andrews2005}, who showed that detection rates of injected
mutants are statistically correlated with detection rates of real
faults from project bug-tracker history. \citet{just2014} provided
a follow-up large-scale study on Java projects that confirmed the
result.

The mutation-testing tool ecosystem includes \textit{PIT} for Java
\citep{coles2016} and \textit{mutmut} for Python. Our mutation
operators (arithmetic, comparison, boundary, return-replacement,
boolean-negation) are the canonical subset implemented by both
tools. \citet{papadakis2019survey} provides the canonical recent survey of
mutation testing, including the equivalent-mutant detection
challenge that we address via ground-truth tests in
\S\ref{sec:methods-mutation}, and the selective mutation strategies
that motivate our per-operator decomposition in
\S\ref{sec:results-peroperator}. \citet{petrovic2018} reports a
large-scale industrial evaluation at Google showing that mutation
testing remains a practically useful signal even at the scale of
large production codebases.

\paragraph{Mutation testing for LLM test generation}
It has been used occasionally in recent work, but no prior study reports
the kind of cross-method cross-LLM mutation-kill-rate matrix that
we provide here. The closest comparison is
\citet{wang2026mutationstudy}, which reports the mutation kill rate as one
of several evaluation metrics in a benchmark of LLMs-generated tests;
their study covers fewer LLMs than ours and does not decompose the
kill rate by operator or by source benchmark.
\citet{papadakis2019survey} surveys the mutation-testing literature and catalogues the operator families that later work builds on, motivating the
kind of operator-level analysis we conduct in
\S\ref{sec:results-peroperator}.

\subsection{Search-based software testing}\label{sec:related-sbst}

Search-based software testing has been the dominant paradigm for
automated test-suite generation since \citet{mcminn2004}'s survey
and \citet{harman2010}'s empirical comparison of search-based
versus random testing. \emph{EvoSuite} \citep{fraser2011,fraser2013}
is the canonical SBST tool for Java, combining genetic-algorithm
test-case search with dynamic symbolic execution. EvoSuite has been
validated repeatedly on industrial codebases \citep{almasi2017} and
remains the reference baseline for Java-language SBST research.

For Python, the corresponding tool is \emph{Pynguin}
\citep{lukasczyk2023empirical,lukasczyk2022}. Pynguin combines
coverage-driven genetic search with dynamic symbolic execution,
optimized for Python's dynamic typing and runtime introspection
capabilities. The Pynguin authors and others have benchmarked it on
standard Python benchmarks (HumanEval, MBPP) and reported
competitive coverage results against test-suite
generation baselines.

\paragraph{Empirical SBST-vs-LLM comparisons}
are recent and limited. \citet{lemieux2023codamosa} is the closest
analog: it combines SBST with LLM prompts and reports improvements
over each approach alone, demonstrating complementarity in coverage
metrics.  Our findings extend the complementarity
observation from coverage to mutation kill rate in Python, and we
identify the operator family (comparison) where the complementarity
is sharpest. To our knowledge, no prior study reports a head-to-head
LLM-method vs.\ Pynguin mutation-kill-rate comparison on matched
Python functions, which is what we provide in
\S\ref{sec:results-pynguin}.

\subsection{Human evaluation of generated code and
  tests}\label{sec:related-humaneval}
  
  Human evaluation of LLM-generated code (and tests) is less mature
  than the literature on automated metrics. \citet{vaithilingam2022}
  at CHI established the foundational observation that developers'
  \emph{expectations} of LLM code-generation tools diverge sharply
  from their lived \emph{experience}, finding that perceived
  usefulness depends heavily on readability and naming conventions
  even when objective correctness is similar. \citet{liang2024copilot}
  extended this observation to a large scale with a 410-developer survey
  of Copilot users at ICSE 2024, identifying readability and integration
  into the developer's existing workflow as the dominant
 quality dimensions—more important to participants than raw
  correctness in many cases. \citet{mozannar2024chi} at CHI 2024
 complements these survey results with a behavioral-trace study of
  how developers actually invoke and edit Copilot's suggestions in
  practice. Together, these three studies establish that
  \emph{human-perceived quality} and \emph{automated-metric quality}
  measure related but non-identical constructs—an observation
 consistent with what we report in
  \S\ref{sec:discussion-moe}, where qwen3-coder achieves a higher
  mutation kill rate than qwen3, but our annotators rate qwen3.5
  higher on all three rubric dimensions.
  
  \paragraph{Human evaluation specifically for LLM-generated unit
  tests}
  is sparser than the broader code-generation literature.
  \citet{siddiq2024junit} reports an empirical evaluation of
  LLM-generated JUnit tests on multiple dimensions
  (compilability, correctness, coverage) but does not include a
  multi-annotator human rating component with formal inter-rater
  agreement statistics. \citet{wang2026mutationstudy} includes a small
  annotation study alongside their automated mutation-testing
  benchmark but, similarly, does not report Cohen's $\kappa$ or
  Krippendorff's $\alpha$ across multiple raters. To our knowledge,
  no prior study reports the kind of three-annotator behaviorally
 anchored 0–5 rubric evaluation of RAG-augmented test generation
  that we present in \S\ref{sec:results-humaneval}.
  
  \paragraph{Rating-scale methodology.}
  The behaviorally-anchored rating scale (BARS) methodology we use
  in our rubric was introduced by \citet{smith1963} in
  industrial-psychology research and has been adapted for many
  software-engineering contexts since. \citet{landis1977} provides
  the canonical interpretation thresholds for Cohen's $\kappa$ that
  we use to assess inter-rater agreement in
  \S\ref{sec:results-humaneval}: $\kappa < 0.20$ slight,
  $\kappa \in [0.21, 0.40]$ fair, $\kappa \in [0.41, 0.60]$ moderate,
  $\kappa \in [0.61, 0.80]$ substantial, $\kappa \geq 0.81$ almost
  perfect. \citet{krippendorff2018} defines the ordinal-$\alpha$
  variant of inter-rater agreement we use as the primary three-rater
 statistic since Cohen's $\kappa$ is defined only pairwise.

\subsection{Empirical SE methodology}\label{sec:related-method}

Our analytical methodology—mixed--effects regression with
\texttt{sample\_idx} as a random intercept, Type-III ANOVA for
unbalanced designs, Tukey HSD post-hoc, and Bonferroni correction
across the family of pairwise tests—follows the standard
recommendations of \citet{wohlin2012} and
\citet{madeyski2024empirical} for analyzing empirical
software-engineering experiments. The Spearman $\rho$ threshold of
$\geq 0.8$ for cross-condition generalization is sourced from
\citet{zar1984} and is the threshold adopted by
\citet{jureczko2015} for defect-prediction-model generalization
across projects, which is the SE literature's nearest analog to
our cross-LLM-method-ranking question.

\subsection{Positioning of the present work}\label{sec:related-positioning}

The present paper sits at the intersection of all six of the above
sub-literatures. Relative to each:

\begin{itemize}
\item \textbf{LLM-based test generation
  (\S\ref{sec:related-llmtg})}: we are the first to report a
  cross-LLM (4 open-weight models, 3B–30B parameters)
  mutation-testing-based evaluation of four RAG-augmentation variants
  on Python unit-test generation.
\item \textbf{RAG for code (\S\ref{sec:related-rag})}: we show that
  lexical retrieval-faithfulness is a model-level rather than a
  method-level property (\S\ref{sec:results-faithfulness}), and that
  the strong negative faithfulness--kill-rate correlation this
  produces at the cell level is an artifact of the model factor. We
  are not aware of prior work in this setting that reports the
  partial correlation alongside the pooled one.
\item \textbf{Mutation testing (\S\ref{sec:related-mutation})}: our
  per-operator and per-benchmark decompositions show that the method
  effect is absent in every scope, and locate the discriminative
  variance in the model factor and in source-problem difficulty
  instead. We are not aware of a prior cross-model mutation study
  that reports a null of this kind at this scale, nor one that pairs
  it with a human-evaluation signal pointing the other way.
\item \textbf{SBST (\S\ref{sec:related-sbst})}: prior work already
  benchmarks LLM test generation against Pynguin on mutation score
  \citep{dakhel2024mutation,straubinger2025debug}. Our contribution
  is the \emph{per-operator} decomposition on a matched function
  set, with identical evaluation pipelines for both outputs, which
  identifies a complementarity axis rather than a winner.
\item \textbf{Human evaluation (\S\ref{sec:related-humaneval})}: our
  three-annotator behaviorally-anchored 0–5 rubric study on 40
  stratified samples is, to our knowledge, the first human
  evaluation of RAG-based test generation that reports formal
  inter-rater agreement statistics.
\end{itemize}

\paragraph{Our null is independently corroborated, and that matters
for how it should be read.}
Two 2026 studies reach compatible conclusions by different routes.
\citet{konstantinou2026newer} replicate four state-of-the-art
LLM-based test-generation pipelines on 393 Java classes and find
that a plain zero-shot prompt \emph{outperforms} all four on line
coverage, branch coverage and mutation score once a current-
generation model is used---by 20.9\% on mutation score---concluding
that the engineering scaffolding around the model has been overtaken
by the model itself. \citet{shin2026ragtest} evaluate RAG for Python
test generation across three knowledge sources and four LLMs and
report that retrieval does \emph{not} improve correctness, yielding
only a 6.5\% line-coverage gain. Our result---that four retrieval
strategies are statistically indistinguishable on defect detection
while the model factor dominates them $21.7\times$---is the same
phenomenon observed on a third axis. A single null is a result about
one experiment; three independent nulls, in two languages, across
retrieval and prompt-engineering scaffolding alike, are evidence
about where the field's effort is currently being misallocated.

\paragraph{What remains open.}
Against that backdrop, three specific gaps motivate this study.

\begin{enumerate}
\item \textbf{No cross-LLM mutation-testing evaluation of RAG
  variants, and no retrieval placebo.} The two studies closest to
  ours each cover half the question: \citet{shin2026ragtest} vary
  retrieval across four LLMs but measure correctness and coverage
  rather than defect detection, and \citet{konstantinou2026newer}
  measure mutation score across three LLMs but vary
  prompt-engineering pipelines rather than retrieval. Neither
  includes a \emph{random-retrieval control}. Without one, ``RAG did
  not help'' cannot be separated from ``the extra context tokens did
  not help'', because a semantic retriever and a random chunk
  sampler differ only in ranking. We report both, and the gap
  between them is 0.3 percentage points
  (\S\ref{sec:results-killrate}). Our model pool is also
  deliberately different: every study in Table~\ref{tab:positioning}
  that reports model counts uses frontier or near-frontier models,
  whereas we evaluate open-weight models from 3B to 30B parameters,
  the range a team can actually self-host.
\item \textbf{No multi-annotator human evaluation of RAG-based test
  generation under a behaviourally-anchored rubric.}
  \citet{zhang2026refrag} assess maintainability and
  understandability analytically, and \citet{foster2025ach} report
  engineer acceptance rates for an industrial deployment, but
  neither elicits blinded per-suite ratings from independent
  annotators. Prior human studies of LLM-generated code evaluate
  general Copilot suggestions
  \citep{vaithilingam2022,liang2024copilot} rather than the question
  of whether retrieval augmentation yields tests developers judge
  better. Pairing that signal with mutation testing on the same
  suites is what exposes the dissociation we report in
  \S\ref{sec:results-humaneval}.
\item \textbf{No per-operator LLM-vs-SBST comparison on matched
  Python functions.} \citet{straubinger2025debug} do compare an
  LLM approach against Pynguin on Python with mutation score, so the
  head-to-head itself is no longer novel. What is missing is the
  \emph{operator-level} decomposition on a matched function set:
  which defect families each paradigm catches, and therefore how
  work should be divided between them. We find the answer is not
  ``LLMs are better'' but a clean split---SBST leads on the
  value-derived families, LLMs on the relational ones
  (\S\ref{sec:results-pynguin}).
\end{enumerate}

\noindent The remainder of this paper addresses all three through a
controlled $4 \times 4$ factorial design (\S\ref{sec:methods})
augmented with a three-annotator human evaluation and a Pynguin
tool-comparison study on matched functions.

\paragraph{Methods.}
\emph{Plain LLM} prompts the model directly with the function under
test and instructions to generate unit tests, with no retrieval.
\emph{Random RAG} augments the prompt with five randomly-selected
text chunks from the same knowledge base
(\S\ref{sec:methods-kb}); this serves as a control for ``does the LLM
benefit from extra context regardless of relevance?''. It is
identical to Simple RAG in every respect---same knowledge base, same
number of chunks, same prompt template, same decoding
parameters---except that the chunks are drawn uniformly at random
instead of by cosine rank, so the contrast between the two isolates
the contribution of retrieval \emph{relevance} from that of
additional context. \emph{Simple RAG} performs a single
cosine-similarity retrieval pass over the same knowledge base,
returning the top $k = 5$ most relevant chunks. \emph{Iterative Critique
RAG} generates a first draft of tests via Simple RAG, then runs a
critique-and-refine loop for two iterations where the model judges
its own output against criteria (coverage, correctness, idioms) and
rewrites accordingly.

\paragraph{Models.}
We selected open-weight models served via Ollama, spanning a
deliberate capability range: a small dense baseline (llama3.2 3B),
a mid-size dense model (phi4 14B), a recent latest-generation dense
model (qwen3.5 9B), and a state-of-the-art code-specialized
mixture-of-experts model (qwen3-coder 30B with 3.3B active
parameters). All models were queried with a temperature of 0.2 and
a 600-second per-run budget. We did not fine-tune any model; the
goal is to characterize how each generation method \emph{uses} a
given off-the-shelf LLM.

\subsection{The retrieval knowledge base}\label{sec:methods-kb}

All three retrieval conditions draw from one corpus, built once and
frozen for the whole study. Because our central result is a null about
retrieval, the corpus must be specified precisely enough for a reader
to judge whether the null is a property of retrieval or of this
particular corpus.

\paragraph{Sources.} We selected 14 URLs covering Python testing
practice: seven \texttt{pytest} how-to pages (assertions,
parametrisation, getting started, fixtures, monkeypatching, output
capture, temporary paths), two CPython standard-library references
(\texttt{unittest}, \texttt{unittest.mock}), four tutorials
(two Real~Python articles, GeeksforGeeks, Semaphore CI) and the
Hypothesis property-based-testing quickstart. \emph{Two of the 14
failed to fetch at build time} and are absent from the index, leaving
12 contributing sources. We report this because the composition is
uneven in a way that matters for interpretation
(Table~\ref{tab:kb}): the two standard-library pages alone supply
46\% of all chunks, while the Hypothesis page---the only
edge-case-oriented source, and the one most plausibly relevant to
killing boundary mutants---supplies 1.1\%.

\paragraph{Indexing.} Each fetched page is reduced to text, then split
into fixed-width overlapping windows of 500 characters with 100
characters of overlap; windows shorter than 50 characters after
stripping are discarded. Overlap ensures that material spanning a
window boundary is not lost from every retrievable unit. This yields
\textbf{964 chunks}, which are embedded with
\texttt{sentence-transformers/all-MiniLM-L6-v2} (384 dimensions) and
held in an in-memory NumPy matrix. Retrieval is exact cosine
similarity against that matrix---there is no approximate index, so
ranking is deterministic given the query.

\paragraph{Querying.} The query is not the bare function. It is a
fixed task prefix, \texttt{``pytest unit testing examples patterns for
python function:''}, concatenated with the first 300 characters of the
function under test. The prefix biases retrieval toward
testing-idiom material rather than toward code resembling the function
body, which is the intended behaviour for a documentation corpus.
Simple RAG and the first iteration of Iterative Critique RAG take the
$k = 5$ highest-scoring chunks; Random RAG takes 5 chunks drawn
uniformly at random from the same 964, using an unseeded generator, so
its draw differs between runs.

the query and the frozen index, so a single example is fully
reproducible and is the clearest way to convey what the retriever
actually supplies. Corpus sample 0 is MBPP/67:

        for j in range(1, i+1):

bunched (0.588--0.636 against a whole-corpus range of
$-0.065$--$0.636$), so the ranking among the top chunks is decided by

sensibly, pulling property-based-testing material for a numeric

anything specific to Bell numbers. Nothing in the retrieved context
tells a model what $B_4$ is. The suite that Simple RAG produced for

supplied itself --- and then six \texttt{pytest.raises} cases for

instrumented retrieval with a \emph{noise rate}: the fraction of
returned chunks scoring below a cosine threshold of 0.3, intended as a
signal for ``the retriever found nothing relevant''. It is identically
zero for every query in the study---no retrieved chunk ever scored
below the threshold. We report this rather than discarding it because
it bounds one explanation of our null: the retriever is not returning
obvious garbage. Whether the above-threshold material is
\emph{useful} is a separate question, and the Random RAG contrast
(\S\ref{sec:results-killrate}) is what actually answers it.

\subsection{Dataset}\label{sec:methods-dataset}

We sampled 100 functions (seed = 42) from the union of HumanEval
\citep{chen2021humaneval} and MBPP \citep{austin2021mbpp},
shuffled into a deterministic order. For the mutation-testing
study, we ran each (technique $\times$ model) combination on all 100 samples, yielding 1{,}600 cells in total ($4 \times 4 \times 100$). After dropping samples whose
LLM-generated test suites failed the original-code filter
(\S\ref{sec:methods-mutation}),
$N_{\text{valid}} = 1{,}443$ cells remained for analysis. The mix of source benchmarks in the 100 sampled functions is 65 MBPP and 35 HumanEval problems---a property of
the seed-42 shuffle that we exploit in
\S\ref{sec:results-perbenchmark} to compare per-benchmark
significance.

\paragraph{Sample size.}
HumanEval (164 problems) and MBPP (974 problems) together contain
1{,}138 candidate functions. Running our 4\,$\times$\,4 generation
matrix on the full union would require
$4 \times 4 \times 1{,}138 = 18{,}208$ LLM-generation cells; each
cell additionally drives up to 15 mutants through a per-mutant
pytest invocation, producing roughly 270{,}000 individual
mutation-test executions and an order-of-magnitude blow-up in
wall-clock cost. On our hardware (NVIDIA A100 40\,GB,
Appendix~\ref{app:hardware}), a single 100-function sweep at the 600\,s per-cell budget consumes approximately $4 \times 4 \times 100 \times 600\,\mathrm{s} \approx 270$ GPU-hours. The 100-function corpus retains ample power for the mixed-effects regression (1{,}600 starting cells across 16 treatment combinations, far above the conventional $n \geq 30$-per-cell threshold for unbalanced ANOVA), while
keeping the experimental campaign within a feasible compute
budget for a single research team. We document the sub-sampling
explicitly so that future replications on larger budgets can
extend our findings to the full benchmark.

\subsection{Mutation testing}\label{sec:methods-mutation}

We adopt \emph{mutation testing} as our SE-relevant evaluation
metric. A mutation operator introduces a small syntactic change to
the function under test, producing a \emph{mutant}. A test suite
\emph{kills} a mutant when at least one of its tests fails on the
mutated function but passes on the original. The proportion of
non-equivalent mutants killed is the \emph{mutation kill rate}—
a behavioral defect-detection metric grounded in the test suite's
ability to discriminate buggy code from correct code
\citep{andrews2005,just2014}.

\paragraph{Mutation operators.}
We implement five operator families covering the canonical mutations
from the \emph{mutmut} and \emph{PIT} literature: arithmetic
operator swap (\verb|+ <-> -|, \verb|* <-> /|), comparison operator
swap (\verb|== <-> !=|, \verb|< <-> >=|, \verb|> <-> <=|), boundary
mutation ($n \leftrightarrow n \pm 1$ on integer constants),
return-value replacement (\verb|return x -> return None|), and
boolean negation (\verb|True <-> False|). For each function, we cap
the total number of mutants at 15 to keep per-cell runtime
tractable; the cap is reached only on the most complex MBPP
functions.

\paragraph{Test filtering.}
Following \citet{andrews2005}, we filter generated tests to retain
only those that pass on the \emph{original} function before
measuring kill rate. This is necessary because LLMs occasionally
generate tests with spurious assertions (e.g., expecting
\texttt{ValueError} when the function raises \texttt{IndexError});
a kill-rate measurement that includes these tests would conflate
generation quality with mutation detection. Concretely, we parse
each test file, isolate individual \texttt{def test\_*} functions,
run each against the original code via pytest in a subprocess, and
assemble a new test file containing only the passing tests. Samples
whose entire generated test suite is dropped by this filter are
reported as NaN and excluded from kill-rate aggregates.

\paragraph{Equivalent mutants.}
A mutant is \emph{equivalent} if it is semantically identical to the
original function (no test can ever kill it). We detect equivalent
mutants by running the corresponding ground truth tests against
each mutant: if the ground truth passes on the mutant, we mark it
as equivalent and exclude it from the denominator of the kill rate.
Approximately 5--15\% of mutants per cell are detected as equivalent
under this rule.

\paragraph{Mutant execution against the original suite.}
Some LLMs—most prominently phi4–14b—prepend a re-definition of
the function under test to their generated test file. When the
mutation harness concatenates the (possibly mutated) function with
this test file, Python's last-definition-wins resolution causes the
LLM's pristine redefinition to shadow the mutant, and the test suite
always exercises the unmutated version. We fix this via an
abstract syntax tree (AST) based strip of any top-level
\texttt{def <function\_name>(...)} block from the test code before
concatenation. The fix is reflected in all
numbers reported in this paper; numbers from a pre-fix run are
documented in our replication package for transparency.

\subsection{Statistical methodology}\label{sec:methods-stats}

The 4,800-cell experimental design is unbalanced (sample sizes
vary across cells after filtering), and the kill-rate distribution
is heavily concentrated at the 0.0 and 1.0 extremes on capable
models, producing a strong ceiling effect. We therefore use a
multi-test strategy.

\paragraph{Per-sample rank tests.}
We compute Kruskal–Wallis omnibus tests across the four methods
within each model and pooled across models, followed by pairwise
Mann–Whitney U tests with Bonferroni correction across the six
method pairs ($\alpha = 0.05/6 \approx 0.0083$). For paired
designs, we additionally compute Friedman omnibus tests and pairwise
Wilcoxon signed-rank tests with the same Bonferroni correction.
Effect sizes are reported as Cohen's $d$ for unpaired comparisons
and Cohen's $d_z$ for paired comparisons.

\paragraph{Mixed-effects analysis.}
We additionally fit a Type-III ANOVA with 
\texttt{kill\_rate $\sim$ C(method) + C(model) + C(sample\_idx)} using all 
valid observations, followed by Tukey HSD post-hoc comparisons on 
the method factor. We complement this with a \emph{linear 
mixed-effects model} treating \texttt{sample\_idx} as a random 
intercept and \texttt{model} and \texttt{method} as fixed effects, 
fit via restricted maximum likelihood (statsmodels MixedLM, lbfgs 
solver). This is the appropriate test for our nested design 
--- same source samples across methods within a model---and gains substantial 
power over the rank tests because it does not require complete 
cases across all four methods.

\paragraph{Per-operator decomposition.}
Because the overall kill rate hits a 1.0 ceiling on the strongest
models, we additionally analyze per-operator kill rates
(arithmetic, boundary, comparison, negate-boolean, return-None)
using the same ANOVA + Mixed-LM + Tukey pipeline.

\paragraph{Per-benchmark decomposition.}
We split per-sample data by source (HumanEval vs MBPP) and re-fit
the ANOVA + Mixed-LM separately within each benchmark.

\paragraph{Cross-model generalizability.}
We compute the Spearman rank correlation $\rho$ between
method-rankings across each pair of models for the overall kill
rate and for each per-operator kill rate. A finding ``generalizes''
if min $\rho \geq 0.8$ across all model pairs.

\subsection{Human evaluation}\label{sec:methods-humaneval}

To complement the automated mutation-testing analysis with a
developer-perceived quality signal, we designed a three-dimension, behaviourally-anchored rating scale and ran a three-annotator study against it. The rubric is our own; the behaviourally-anchored format follows \citet{smith1963}, and we interpret agreement using the thresholds of \citet{landis1977} with ordinal Krippendorff's $\alpha$ \citep{krippendorff2018} as the primary three-rater statistic.

\paragraph{Sample selection.}
We drew 40 stratified \texttt{(function, generated\_tests)} pairs
from the mutation-testing checkpoints, balanced across the 16
(method $\times$ model) cells and across the HumanEval/MBPP source
split (23 MBPP + 17 HumanEval pairs in the final worksheet).
Method and model identifiers were stripped from the worksheet so
annotators could not infer which generator produced each test
suite; the private mapping is preserved in a separate metadata
file kept off-version-control.

\paragraph{Rubric.}
Annotators rated each pair on three behaviorally-anchored 0
–5 scales: \emph{test idiom quality} (pytest style: parametrize,
fixtures, naming, assertion structure), \emph{correctness} (would
every test pass on a correct implementation?), and
\emph{completeness} (coverage across the happy path, edge cases, and
error cases). Each anchor description is shown directly beneath the
corresponding radio button in the annotation UI, so annotators do
not need to recall the rubric from memory.

\paragraph{Annotation platform.}
We built a Streamlit web application that presents one
(function, test-suite) pair at a time with side-by-side
syntax-highlighted views, the rubric in the sidebar, and per-sample
save-and-resume. Annotators log in with a short identifier, and the
app writes their ratings to a per-annotator CSV after every
\emph{Save \& Next} click.

\paragraph{Annotators.}
Three independent annotators rated all 40 samples. All annotators
held a graduate-level computer-science background and had at least
two years of Python development experience.

\paragraph{Inter-rater agreement.}
We report pairwise Cohen's $\kappa$ with linear weighting for
ordinal data, plus Krippendorff's $\alpha$ with the ordinal metric as
the primary three-rater statistic. Because the ordinal difference
function is defined with respect to the observed marginal
distribution rather than as a fixed distance, the metric must be
named whenever an $\alpha$ is reported; we give the interval and
nominal values alongside the ordinal one in
\S\ref{sec:results-humaneval} so the figure is interpretable
independently of that choice. Our implementation
(\texttt{krippendorff\_alpha.py}) reproduces the worked example in
\citet{krippendorff2018} to three decimal places on both the nominal
and interval metrics, and the self-test runs on every invocation.
Agreement targets follow \citet{landis1977}: $\geq 0.4$ moderate,
$\geq 0.6$ substantial.

\subsection{Tool comparison---Pynguin baseline}\label{sec:methods-pynguin}

To ground our LLM-method results against the prior dominant paradigm
in automated unit-test generation, we benchmarked our LLM-based
methods against \emph{Pynguin 0.45.0} \citep{lukasczyk2022}. We
selected Pynguin because: (i) it is Python-native, like our
generators (in contrast to EvoSuite, which targets Java); (ii) it
is open-source and reproducible (in contrast to GitHub Copilot's
test-generation feature, which is closed); and (iii) it is the
de-facto reference SBST baseline in recent Python testing research.

We ran Pynguin on the same 40 functions used in the human-evaluation
study, giving each function a 60-second search budget. Pynguin's
generated tests reference the function via an alias prefix
(\texttt{module\_0.fn}); we rewrote these references to bare
function calls so the mutation harness could resolve them. Aside
from this purely-syntactic rewrite, we did not modify any of the
tests Pynguin produced. The rewritten tests were then evaluated
through exactly the same mutation-testing pipeline
(\S\ref{sec:methods-mutation}) as the LLM-generated tests, yielding
a directly-comparable kill-rate metric.

\subsection{Statistical significance}\label{sec:results-stats}

\paragraph{\textnormal{\textbf{RQ2} --- Is the method effect significant once sample difficulty and model are controlled, and does it concentrate anywhere?}}
\emph{Answer: no, and no.} The method factor is not significant in
any scope, and the per-benchmark and per-operator decompositions
(\S\ref{sec:results-perbenchmark}, \S\ref{sec:results-peroperator})
locate no family in which it becomes so.


\subsubsection{Overall kill rate}\label{sec:results-stats-overall}

Despite the descriptive ordering in
Table~\ref{tab:killrate-matrix}, \emph{the method effect on the
overall kill rate is not statistically significant} after
controlling for model and source sample. A Type-III ANOVA on
\verb|kill_rate ~ C(method) + C(model) + C(sample_idx)|
($n = 1{,}443$ valid observations) reports method $F = 0.209$, $p = 0.890$ (Table~\ref{tab:anova-overall}). The Tukey

$\alpha = 0.05$; the widest pair (Iterative Critique vs Plain LLM, $\Delta = -0.016$) is nowhere near the threshold ($p_{\text{adj}} = 0.838$). The mixed-effects model yields the same conclusion: Plain LLM's contrast against IC is $\beta = +0.001$, $p = 0.972$.

\paragraph{How the spreads are computed.} Because the test filter
leaves cells of unequal size (\S\ref{sec:results-attrition}), the
method and model spreads depend on the estimator, and we state ours.
Our headline figures average the 16 cell means with equal weight:
method spread 0.011, model spread 0.232, ratio $21.7\times$. This is
the appropriate estimator for an unbalanced design, because a
method that loses more suites on the weakest model would otherwise
have its mean computed over a disproportionately easy subset.
Weighting instead by observation count gives method spread 0.016,
model spread 0.228 and a ratio of $14.7\times$. The two differ
because Iterative Critique contributes 50 of its 297 observations
from llama3.2 against Plain LLM's 95 of 395, so the weighted mean
flatters Iterative Critique. \emph{Both estimators support the same
conclusion}---the model factor dominates by more than an order of
magnitude---and we report the balanced one as primary and the
weighted one here so that either reproduction route lands on a
number this paper states.

We return to this finding in \S\ref{sec:discussion-llm-dominates}.

\subsubsection{Per-benchmark decomposition}\label{sec:results-perbenchmark}

\emph{The method effect on boundary kill rate is null on both
source benchmarks.} We decomposed the analysis by source benchmark
because MBPP problems lean more heavily on numeric range and
off-by-one conditions than HumanEval problems do, which gave us an
a priori reason to expect the boundary operator family to separate
methods on MBPP if it separated them anywhere. It does not. On MBPP
($n = 521$) the ANOVA reports $F = 0.94$, $p = 0.421$; on HumanEval
($n = 403$), $F = 0.49$, $p = 0.691$; pooled ($n = 924$),
$F = 0.61$, $p = 0.606$. No Tukey pair survives correction in any
scope, and the mixed-effects model agrees in all three
(Table~\ref{tab:perbench}).

The largest raw contrast is Iterative Critique over Plain LLM on
MBPP ($\Delta = -0.090$, i.e.\ 9.0 percentage points in IC's
favour), which is both the direction and roughly the magnitude a
reader would expect from the refinement loop---but at
$p_{\mathrm{adj}} = 0.216$ it is indistinguishable from sampling
noise at this corpus size. Figure~\ref{fig:boundary-heatmap} shows
the $4 \times 4$ boundary matrix: within-row spread is wider than on
the overall kill rate (Figure~\ref{fig:heatmap}), so boundary
remains the operator family with the most between-method movement on
our suite, but the movement is not systematic with respect to
method.

A pilot run of this study, on a 30-function subset, reported a
significant MBPP boundary effect (ANOVA $F = 2.96$, $p = 0.035$;
Tukey $p_{\mathrm{adj}} = 0.025$). That effect did not replicate
when the corpus was extended to 100 functions. We report this
explicitly because the direction and mechanism remain plausible and
a larger corpus may well recover it; what we cannot claim is that
our data support it.

\subsection{Benchmark contamination}\label{sec:results-contamination}

HumanEval and MBPP were both published in 2021 and ship their
reference solutions \emph{and} their canonical test suites. Every
model in our pool has a training cutoff after that date. A model may
therefore be reciting a memorised suite rather than reasoning about
the function, and if methods differ in how much they recite, the
method factor is confounded with memorisation rather than
measuring generation quality.

\paragraph{Design.} We re-ran the full $4 \times 4$ sweep on a
decontaminated variant of the corpus, built by applying
semantics-preserving transformations that break surface recall while
leaving behaviour identical: the function is renamed via AST rewrite
with all recursive references updated, its parameters are renamed
from a fixed alias table, and the reference tests are rewritten to
call the renamed function. All transformations are deterministic, so
the decontaminated corpus is itself reproducible. Every transformed
problem must still pass its own rewritten reference tests; two of the
100 failed that check and were dropped rather than carried forward,
since a transform that changed behaviour would confound the
comparison with plain breakage. The decontaminated arm therefore
covers 98 functions, yielding 1{,}421 valid observations over
9{,}404 mutants.

We deliberately did \emph{not} paraphrase docstrings with an LLM.
Doing so would break recall more thoroughly but would make the corpus
non-reproducible and unauditable, which is the wrong trade for a
study whose central claim is a null. Docstring text is left intact,
and we state the consequence plainly in
\S\ref{sec:limitations-internal}: our transformation defeats
\emph{lexical} recall of the function signature, not recall keyed on
the problem description.

\paragraph{Result.} \emph{Decontamination does not reduce kill rates,
and does not change the method-level conclusion.} Kill rates move
slightly \emph{upward} under renaming---mean paired change
$+0.0120$ across the 1{,}313 observations present in both arms, with
13 of 16 cells improving---and the change is not significant
(Wilcoxon signed-rank $p = 0.101$). Per-method means are Plain LLM
0.892, Random RAG 0.903, Simple RAG 0.893 and Iterative Critique
0.901, a spread of \textbf{0.0108} against 0.0156 on the original
corpus. The Type-III ANOVA on the decontaminated arm returns method
$F = 0.072$, $p = 0.975$---a weaker method effect than the original
null, not a stronger one---while the model factor remains
overwhelming ($F = 82.9$, $p < 10^{-40}$).

\paragraph{Interpretation.} Two readings are available and we can
distinguish them. If the models were reciting memorised suites,
renaming the function should have degraded performance; it did not.
The small upward movement is most plausibly an artifact of the
transformation itself: renaming \texttt{has\_close\_elements} to a
neutral identifier removes a semantic hint that a model might
otherwise use to produce a plausible-but-wrong test, so marginally
more generated suites survive the original-code filter. What we can
rule out is the strong contamination hypothesis---that our kill rates
are inflated by recall and would collapse on unseen problems. What we
cannot rule out is recall keyed on the problem \emph{description},
which our transformation leaves untouched.

\subsection{Test-filter attrition and the matched subset}
\label{sec:results-attrition}

fails against the \emph{original, unmutated} function is discarded,
because a suite that cannot pass on correct code cannot
meaningfully be said to detect a defect in it. This filter does not
fall evenly across methods, and the imbalance is large enough to
confound any naive comparison of cell means
(Table~\ref{tab:attrition}).

Random RAG         & 80 & 96  & 99  & 99  \\
Simple RAG         & 87 & 94  & 96  & 100 \\
\textbf{Iterative Critique} & \textbf{50} & \textbf{71} & \textbf{77} & \textbf{99} \\
\bottomrule
\end{tabular}
\end{table}

\emph{Iterative Critique loses half its suites on the weakest
model.} Attrition rises monotonically as model capability falls, and
within every model Iterative Critique is the most heavily filtered
method: 50 of 100 on llama3.2 against Plain LLM's 95. The mechanism
is that the refinement loop produces more behaviorally specific
assertions, and a specific assertion that is \emph{almost} right
fails on the original function, taking the whole suite with it. A
broad structural assertion is more likely to be vacuously true and
therefore to survive.

This matters for interpretation in two directions. It inflates the
surviving cells of the heavily-filtered methods, because what
survives is the easier subset; and it means per-cell means are
computed over different populations of functions. To separate the
method effect from the attrition effect, we repeat the central
analysis on the \emph{matched subset}: the functions for which all
four methods produced a suite that passed the filter on the same
model. This yields 273 function-model units (1{,}092 observations;
38 functions on llama3.2, 64 on phi4, 73 on qwen3.5, 98 on
qwen3-coder).

\emph{The method effect remains absent on the matched subset.} Mean
kill rates are Plain LLM 0.895, Random RAG 0.906, Simple RAG 0.896,
Iterative Critique 0.897---a spread of 0.011, against 0.016 on the
full corpus. Matching removes the apparent reordering (Iterative
Critique moves from last to second) without producing a method
effect, which is the expected signature of attrition acting as
noise on the ranking rather than as a source of the null. We
therefore report the full-corpus analysis as primary, with per-cell
$n$ disclosed in every table, and treat the matched-subset result as
a robustness check rather than a separate finding.

\subsection{Retrieval faithfulness is a model property, not a
method property}\label{sec:results-faithfulness}

\paragraph{\textnormal{\textbf{RQ4} --- Does faithfulness to retrieved context predict kill rate?}}
\emph{Answer: no.} The strong pooled association is produced by
the model factor and does not survive controlling for it.


Token-overlap faithfulness between generated tests and retrieved
context varies by model, not by retrieval method. A one-way model on
the eleven RAG cells attributes $R^2 = 0.889$ of faithfulness
variance to the LLM ($p = 0.001$) and $R^2 = 0.118$ to the
generation method ($p = 0.605$): llama3.2 lifts vocabulary from the
retrieved context at $\approx 0.18$ regardless of whether retrieval
was semantic or random, while qwen3.5 sits at $\approx 0.07$.

\emph{The design produces an aggregate correlation that does not
survive the obvious control, and we report it as a cautionary
result.} Pooled across the eleven cells, faithfulness correlates
strongly and negatively with mutation kill rate (Pearson
$r = -0.907$, $p < 0.001$), which invites the reading that lexical
copy-paste harms defect detection. It does not survive controlling
for model: the partial correlation is $r = +0.079$ ($p = 0.818$), a
mixed-effects model with the LLM as a random intercept puts the
faithfulness slope at $\beta = -0.011$ ($p = 0.958$), and the
within-model correlations are \emph{positive} on two of the three
models with enough cells to compute one (llama3.2 $r = +0.948$;
phi4 $r = +0.425$). Weaker models both copy more and kill fewer
mutants; the pooled correlation is between two consequences of model
capability, not evidence of a causal path from one to the other.

We flag this explicitly because cell-level correlations over a
$4 \times 4$ matrix are common in the RAG-for-code literature and
the design admits this failure mode by construction. With sixteen
cells and one factor explaining 99.5\% of outcome variance
(\S\ref{sec:results-stats-overall}), almost any model-varying covariate
will correlate with the outcome at $|r| > 0.8$. A per-function
pairing of faithfulness to kill rate---which our artifacts do not
support, since faithfulness is logged as a cell mean by a separate
generation harness---would be required to make a claim in either
direction.

The LLM-judge faithfulness signal behaves the same way and is null
in both readings (pooled $r = -0.493$, $p = 0.124$; partial
$r = +0.298$, $p = 0.374$). The noise-rate signal is degenerate: our
knowledge base never returns a chunk below the cosine $< 0.3$
threshold, so \texttt{avg\_noise\_rate} is identically $0.0$ across
every cell and cannot be correlated with anything. We report it for
transparency rather than as a result.

\emph{Iterative Critique ranks highest on every dimension} in the
three-annotator means, with the largest IC-vs-Plain-LLM gap on
completeness (4.58 vs 3.63). Three properties of the design and the
analysis are worth establishing before that ranking is relied on.

\paragraph{Method is not confounded with model.} The 40 pairs were
stratified over the $4 \times 4$ matrix, giving 1--3 pairs per cell
(mean 2.5) and 9--11 pairs per method. A rating advantage could
therefore in principle reflect a method's pairs having been drawn
from stronger models. They were not: the method-by-model allocation
is balanced ($\chi^2 = 1.56$, $p = 0.997$).

\paragraph{The effect is not an artifact of pseudo-replication.}
Treating 120 ratings as independent observations would overstate
significance, since they are 40 units rated three times. Repeating
the Kruskal--Wallis test on per-unit means across annotators
($n = 40$) preserves both conclusions: idiom $H = 9.64$,
$p = 0.022$; completeness $H = 14.95$, $p = 0.002$; correctness
remains non-significant ($H = 4.69$, $p = 0.196$).

\paragraph{The effect survives controlling for model and annotator.}
A mixed-effects model of rating on method and model, with annotator
as a random intercept, is the appropriate test and gives the
strongest version of the result. Against Plain LLM, Iterative
Critique scores $\beta = +0.869$ ($p = 0.0001$) on idiom and
$\beta = +0.987$ ($p < 0.0001$) on completeness; correctness is not
significant ($\beta = +0.368$, $p = 0.176$). \emph{Random RAG also
beats Plain LLM on idiom} ($\beta = +0.600$, $p = 0.006$), which is
the human-judgement analogue of the mutation-side result that a
random-chunk placebo performs as well as semantic retrieval: adding
context improves the \emph{perceived} quality of a test suite
whether or not the context is relevant to it.

\paragraph{Agreement is poor in level but not in direction.}
\emph{Inter-rater agreement was below the conventional $\geq 0.4$
threshold} on all three dimensions (ordinal Krippendorff's
$\alpha = -0.001 / -0.127 / +0.304$ for idiom, correctness, and
completeness; the interval metric gives $-0.027 / -0.115 / +0.328$
and the nominal metric $-0.095 / -0.016 / +0.151$, so the conclusion
does not depend on the choice). Pairwise Cohen's $\kappa$ analysis
(Table~\ref{tab:humaneval-kappa}) reveals the cause: \emph{two of
the three annotators (GS and BV) agreed at fair-to-moderate levels}
($\kappa = 0.32$--$0.46$), but the third annotator (SA) used
systematically lower scale values—mean ratings of
$2.88 / 3.45 / 3.62$ versus GS's $4.40 / 4.25 / 4.08$ and BV's
$3.77 / 3.98 / 4.22$. Figure~\ref{fig:annotator-bias} visualizes
this scale-usage bias.

This matters for how the ranking should be read. Krippendorff's
$\alpha$ measures agreement on \emph{absolute} ratings; a rater who
applies the same ordering a scale-point lower throughout will score
near zero on it while still agreeing about which method is better.
That is what happened here. On completeness, all three annotators
independently rank Iterative Critique first. On idiom and
correctness, the two annotators who agree with each other do so as
well, while SA ranks Simple RAG and Plain LLM first respectively. We
therefore do not claim unanimity, and the mixed-effects model above
is the right basis for the ranking rather than the raw means: with
annotator as a random intercept, a constant per-rater offset is
absorbed rather than treated as disagreement about the methods. The
honest summary is that \emph{the ordering is supported on idiom and
completeness and unsupported on correctness}, and that a replication
should calibrate annotators on shared anchor examples before
rating---which we did not do, and which is the most likely source of
the scale divergence.

\subsection{Summary of findings}\label{sec:results-summary}

Five findings appear robust to the limitations cataloged in
\S\ref{sec:limitations}:

\begin{enumerate}
\item \emph{Mutation kill rate scales with LLM capability, not with
  RAG-method choice.} Moving from llama3.2 to qwen3.5 raises mean
  kill rate by 0.232; the entire spread across the four generation
  methods is 0.011, and Iterative Critique sits 0.002 \emph{below}
  unaugmented prompting. Model choice moves the metric
  $21.7\times$ as far as method choice. Spreads here are computed over
  the 16 cell means, giving each (method, model) cell equal weight;
  because cell sizes differ after the test filter
  (\S\ref{sec:results-attrition}), the observation-weighted estimate
  differs and is reported alongside it in
  \S\ref{sec:results-stats-overall}.
\item \emph{Method rankings do not generalize across LLMs.} The best
  method differs on three of four models and Iterative Critique
  leads on none. The only metric clearing $\rho \geq 0.8$ is
  return-None kill rate (mean $\rho = +0.90$), the operator family
  all methods kill easily.
\item \emph{Retrieval faithfulness is a property of the model, not
  of the retrieval method} ($R^2 = 0.889$ by model vs $0.118$ by
  method). An apparent strong negative correlation between
  faithfulness and kill rate ($r = -0.907$) is entirely confounded
  by model and vanishes under control ($r = +0.079$, $p = 0.818$).
\item \emph{Three independent annotators ranked Iterative Critique
  highest on all three quality dimensions.} Controlling for model
  with annotator as a random intercept, the advantage over Plain LLM
  is $\beta = +0.869$ ($p = 0.0001$) on idiom and $\beta = +0.987$
  ($p < 0.0001$) on completeness; correctness shows the same ordering
  but is not significant ($\beta = +0.368$, $p = 0.176$). This
  \emph{contradicts} the mutation-testing result, and the two signals
  are uncorrelated at the suite level ($r = +0.18$, $p = 0.30$).
  Inter-rater agreement is poor in absolute level
  (\S\ref{sec:results-humaneval}), so the ordering rests on the
  model-controlled estimate rather than on raw means.
\item \emph{LLM methods outperform Pynguin's SBST on mutation kill
  rate} under a 60-second budget, with the gap concentrated on
  comparison-operator mutators.
\end{enumerate}

\section{Discussion}\label{sec:discussion}

\paragraph{Why does no method separate, even on the operators
designed to separate them?}\label{sec:discussion-boundary}

The operator-level pattern (\S\ref{sec:results-peroperator}) points
at \emph{assertion specificity} as the axis on which the methods do
differ, even though the difference never reaches significance.
Boundary mutators introduce small numeric perturbations that produce
different return values but identical types and structural shapes. A
test of the form \verb|assert sort_descending([3,1,2])[-1] == 1|
kills a boundary mutation that drops the last element; a test of the
form \verb|assert isinstance(result, list) and len(result) == 3|
does not. Iterative Critique's refinement loop drives generated
tests toward the former category, which is consistent with its
leading the field on arithmetic and boundary mutants---by 2.7 and
3.9 percentage points respectively.

What stops this becoming a method effect is that the same shift
costs it elsewhere. Value-specific assertions are narrow, and the
negate-boolean and return-None families are killed cheaply by the
broad structural assertions that Iterative Critique refines away;
there it is last, by 8.4 and 4.6 points. The gains and losses are of
the same order and they cancel. A reader expecting refinement to
help should therefore expect it to help on the mutants that need
precision and hurt on the mutants that need breadth, with a null in
the pooled metric---which is what we observe. We consider this a
more informative reading of the null than attributing it to
insufficient power, since the power analysis
(\S\ref{sec:limitations-conclusion}) rules out effects larger than
roughly three percentage points and the observed per-operator
movements sit just below that bound.

\paragraph{Why does the method ordering not generalize across LLMs?}
\label{sec:discussion-generalisability}

Two mechanisms contribute, and both argue that the orderings are
substantially artifactual.

The first is \emph{test-filter dropout asymmetry}. Iterative
Critique's refinement loop produces more behaviorally-specific
assertions, and when an assertion is \emph{almost} right but not
exactly right the filter drops the whole suite. The effect is
severe and uneven: Iterative Critique retains only 50 of 100
functions on llama3.2 against Plain LLM's 95, so the two methods'
means are computed over different and differently-difficult
subsets. This is why Plain LLM attains the highest mean on
llama3.2 despite being the weakest method on the other three
models---it is the method whose surviving subset is least filtered.
The matched-subset analysis (\S\ref{sec:results-attrition})
confirms the direction: restricting to the 273 function-model
units where all four methods produced a valid suite leaves a method
spread of 0.011, against 0.016 on the full corpus, so attrition
shuffles the ordering without creating a method effect.

The second mechanism is \emph{a ceiling effect}. Across the whole
corpus, 73.2\% of per-sample kill rates sit at exactly 1.0, and on
the three stronger models the methods are compressed into a band of
0.017--0.031. Rank orderings over a band that narrow are determined
by a handful of functions; two of our sixteen cells are separated
in the fourth decimal place
(\S\ref{sec:results-generalisability}). \emph{Non-generalization
here is better read as the absence of a stable ordering to
generalize than as a method-by-model interaction.}

\paragraph{Divergence between human ratings and kill rate across the two qwen models.}
\label{sec:discussion-moe}

On per-model human ratings (\S\ref{sec:results-humaneval}),
qwen3.5 (9B dense) ranks higher than qwen3-coder (30B MoE) in all
three dimensions, despite qwen3-coder having the higher mutation
kill rate. Our hypothesis is that \emph{qwen3-coder's MoE
architecture produces tests with correct oracles but syntactic
patterns that look slightly off to a human reader}: occasional
bare assertions without \texttt{test\_*} function wrappers,
unusual variable naming (\texttt{var\_0}, \texttt{result\_2}), and
a tendency to chain multiple unrelated assertions in a single test.
This is methodologically important: \emph{mutation kill rate and
human-perceived test quality are not the same construct}.

\paragraph{Why cell-level correlations mislead in cross-model
designs.}\label{sec:discussion-faithfulness}

The faithfulness analysis (\S\ref{sec:results-faithfulness}) is the
clearest methodological lesson in our data, and it is a negative
one. Pooled over eleven cells, token-overlap faithfulness predicts
kill rate at $r = -0.907$---a correlation strong enough to carry a
contribution, and one we initially reported as such. It is an
artifact of aggregation. Faithfulness is a model-level trait
($R^2 = 0.889$ by model against $0.118$ by method): weaker models
echo more of the retrieved vocabulary back, which is the same thing
as saying they template rather than reason. Kill rate is also a
model-level trait, even more strongly
($R^2 = 0.995$, \S\ref{sec:results-stats-overall}). Correlating two
model-level traits across cells that vary the model recovers the
model factor, not a relationship between the traits.

The templating mechanism we originally proposed---that echoing a
generic testing-tutorial chunk yields generic structural assertions
that fail to kill mutants---remains a plausible account of
\emph{why} weak models score high on lexical faithfulness. What our
data cannot do is establish that the echoing causes the lower kill
rate, as opposed to both following from limited capability. Within
a fixed model, where that causal question is actually posed, the
association is positive or absent.

The generalizable warning is structural rather than specific to
faithfulness: in a $4 \times 4$ cross-model design where one factor
dominates the outcome, any covariate that tracks that factor will
correlate with the outcome at $|r| > 0.8$, and the standard
cell-level analysis cannot distinguish that from a finding. The
remedy is to report the partial correlation alongside the pooled
one, or to log the covariate per function so the relationship can be
estimated within model.

\paragraph{SBST and LLM-based test generation are complementary.}
\label{sec:discussion-sbst}

\emph{On arithmetic and negate-boolean operators Pynguin
outperforms every LLM method}, including Iterative Critique (0.850
vs 0.809 on arithmetic; 1.000 vs 0.917 on negate-boolean). The LLM
advantage concentrates on the two operator families that require a
relational or value-boundary judgement: comparison, where the gap is
very large (0.917 vs 0.250), and boundary (0.817 vs 0.554). These
two families carry the LLM lead in the pooled kill rate (0.898--0.922
vs 0.787, Mann--Whitney $p < 0.001$ for every method against
Pynguin).
\emph{Pynguin's behavioral oracles are derived from observed return
values}, not from operator-level semantics, which explains both
halves of the pattern: value-derived assertions catch numeric
perturbation reliably and miss relational-operator substitution
almost entirely. The hybrid architecture this implies is sharper
than ``use both'': \emph{use SBST for the value-sensitive operator
families and an LLM for relational oracles}. We note the comparison rests on the 34 functions
for which Pynguin produced a valid suite, under a 60-second budget
(\S\ref{sec:limitations-external}).

\paragraph{LLM capability dominates retrieval design.}
\label{sec:discussion-llm-dominates}

For a team deploying an LLM-based test generator, \emph{this result
inverts the usual framing}. The question that moves the metric is not
``which retrieval strategy?'' but ``which open-weight model, at what
cost per suite?''. Across our pool, moving from a 3B to a 9B model
buys 0.232 in mean kill rate; every retrieval strategy we tried, from
a random-chunk placebo to a two-round critique loop, fits inside a
band of 0.011. Retrieval design is not where the engineering effort
pays off at this scale.

\section{Implications}\label{sec:implications}

\subsection{For practitioners}\label{sec:implications-practice}

\begin{enumerate}
\item \textbf{Spend the budget on model selection, not retrieval
  engineering.} Model choice moved defect detection $21.7\times$
  further than method choice. A team choosing between a larger model
  and a more sophisticated RAG pipeline, at equal cost, should take
  the model.
\item \textbf{Do not assume a documentation knowledge base earns its
  keep---measure it against a random-retrieval control.} Semantic
  ranking over our testing-documentation corpus beat random chunks
  from the same corpus by 0.3 percentage points. Retrieval that
  cannot beat its own placebo is adding latency and tokens for
  nothing. The control costs one extra experimental arm and is the
  only way to tell the two apart.
\item \textbf{Do not treat developer-perceived quality as a proxy for
  defect detection.} Our annotators consistently preferred Iterative
  Critique's tests---significantly so on idiom and completeness---and
  those tests detect no more defects than unaugmented prompting.
  Teams optimising a review-based or rubric-based quality signal
  should expect it not to move fault detection, and should measure
  both.
\item \textbf{Divide work between SBST and LLM generators by operator
  family, not wholesale.} Pynguin led every LLM method on arithmetic
  (0.850 vs 0.809) and negate-boolean (1.000 vs 0.917) mutants, while
  LLMs led decisively on comparison (0.917 vs 0.250) and boundary
  (0.817 vs 0.554). A hybrid should route by the kind of oracle
  required, not run both and merge.
\item \textbf{Account for test-filter attrition when comparing
  methods.} Iterative Critique produced a usable suite for only 50 of
  100 functions on our weakest model, against Plain LLM's 95.
  Comparing mean quality across methods without reporting yield
  compares different populations of functions.
\end{enumerate}

\subsection{For researchers}\label{sec:implications-research}

\begin{enumerate}
\item \textbf{Report the partial correlation alongside the pooled one
  in cross-model designs.} Our faithfulness result is a cautionary
  case: a pooled $r = -0.907$ ($p < 0.001$) became $r = +0.079$
  ($p = 0.818$) under control for model. Where one factor explains
  99.5\% of outcome variance, any covariate tracking that factor will
  correlate with the outcome at $|r| > 0.8$. Cell-level correlation
  over a $4 \times 4$ matrix cannot distinguish that from a finding.
\item \textbf{Include an unaugmented and a placebo condition.} Much
  of the RAG-for-code literature compares a proposed retrieval design
  against a weaker retrieval design. Without a no-retrieval arm the
  question ``does retrieval help?'' is not asked, and without a
  random-retrieval arm ``does \emph{relevance} help?'' is not
  separable from ``do extra tokens help?''.
\item \textbf{Treat the model factor as a first-class experimental
  variable.} Method rankings in our data do not transfer: the best
  method differs on three of four models, and only the kill rate of
  the easiest operator family clears a $\rho \geq 0.8$ agreement
  threshold across all model pairs. A technique validated on one
  model should not be reported as a general result.
\item \textbf{Report kill rate distributions, not only means.}
  73.2\% of our per-sample kill rates sit at exactly 1.0. On a
  ceiling that high, mean differences are driven by a small tail, and
  parametric comparisons of means overstate what the data can
  resolve.
\item \textbf{Publish nulls in this area.} Two independent 2026
  studies reach compatible conclusions by other routes
  (\S\ref{sec:related-gap}). The cumulative signal is only visible
  because those nulls were reported.
\end{enumerate}

\section{Threats to Validity}\label{sec:limitations}

We organize the limitations along Wohlin et al.'s
\citep{wohlin2012} standard taxonomy.

\subsection{Construct validity}\label{sec:limitations-construct}

\paragraph{Mutation kill rate is a proxy.}
The five-operator set we adopt is the canonical subset from
\emph{mutmut} and \emph{PIT}, but the kill-rate numbers should be
read as relative comparisons between methods rather than absolute
ground-truth defect-detection rates.

\paragraph{Human ratings have low absolute calibration; we treat
them as ordinal-only.}
Our three-dimensional 0--5 rubric did not achieve the conventional
$\geq 0.4$ Cohen's $\kappa$ threshold on two of the three
dimensions. Pairwise agreement between two of three annotators
reached fair-to-moderate levels ($\kappa = 0.32$--$0.46$); the
third annotator (SA) systematically used the lower half of the
0--5 scale, dragging the three-rater Krippendorff's $\alpha$ below
zero on test-idiom and correctness. We do not claim that the
absolute mean ratings in Table~\ref{tab:humaneval-method} are a
calibrated quality scale. Instead, we use the \emph{rank ordering
of methods} as the human-evaluation signal: every annotator,
viewed individually, ranked Iterative Critique first on completeness,
and the rank ordering of the four methods is consistent across all
three annotators in two of the three dimensions despite their
scale-usage divergence. Methodologically, we read this as evidence
that \emph{rigorous LLM-test-quality evaluation requires a
rubric-calibration training session before annotation}---a finding
that future work in this area should treat as a default protocol
requirement, not an optional refinement. We recommend a
multi-pass calibration protocol (annotators rate a shared training
set, discuss divergence, re-anchor, then rate the production set)
of the kind common in clinical-coding inter-rater studies. The
results we present should therefore be read as \emph{ordinal
evidence consistent with the mutation-testing ordering}, not as a
calibrated absolute quality scale.

\subsection{Internal validity}\label{sec:limitations-internal}

\paragraph{The test filter introduces a confound.}
The \verb|_filter_passing_tests| step drops a larger fraction of
Iterative Critique's tests than that of Plain LLM's. IC's reported
kill rate is therefore averaged over fewer surviving samples per
cell than Plain LLM's. We considered two competing explanations
for this asymmetry. The first is that IC's refinement loop produces
more behaviorally-specific assertions that, when off by a small
margin (e.g., expecting \texttt{[1, 2, 3]} but the function returns
\texttt{[1, 2, 3, 0]}), fail the filter rather than fail on a
mutant---in which case the filter is selecting the most precise IC
tests for inclusion. The second is that IC's critique-and-refine
loop is genuinely more hallucination-prone (the model invents
constraints not present in the docstring) and the filter is
disproportionately catching IC's fabrications. Both effects are
plausible; our data cannot fully separate them, and the IC kill
rate in Table~\ref{tab:killrate-matrix} should be interpreted as
``the kill rate of IC tests that survive the filter,'' not ``the
kill rate of all IC tests.'' The Mixed-LM analysis using the full
per-sample data, without requiring balanced cells, preserves the
direction of the effect, but a future replication should compare
\emph{pre-filter assertion semantics} between IC and Plain LLM to
resolve which mechanism dominates.

\paragraph{Annotators were not calibrated before rating.}
The three annotators received the rubric and its behavioural anchors
but did not rate shared practice examples before the study, and one
of the three used the scale roughly a point lower than the other two
throughout (\S\ref{sec:results-humaneval}). Krippendorff's $\alpha$
is consequently near zero on two of the three dimensions even though
the method ordering is largely shared. The mixed-effects model
absorbs a constant per-rater offset, so the reported effects are not
driven by this, but a replication should run a calibration round on
shared anchors and report $\alpha$ after it. With 40 pairs over 16
cells (1--3 per cell) the study is also small; it is adequate for the
method contrast, which is what it was powered for, and not for
per-model claims about perceived quality.

\paragraph{Decontamination defeats signature recall, not
description recall.}
Our decontamination pass (\S\ref{sec:results-contamination}) renames
the function and its parameters but leaves the docstring intact, a
choice made so the transformed corpus stays deterministic and
auditable. A model that memorised a HumanEval suite keyed on the
problem \emph{description} rather than on the identifier would be
unaffected by our transformation, and our result---that kill rates
do not fall under renaming---would not detect it. The stronger test,
paraphrasing docstrings with an LLM, trades reproducibility for
coverage of that case; we judged the trade wrong here but it is the
natural next step for a replication that can afford to publish the
paraphrased corpus alongside its results.

\subsection{External validity}\label{sec:limitations-external}

\paragraph{Four LLMs is not a population.}
A future replication should test at least one closed-weight model
(e.g., GPT-4o-mini, Claude Sonnet 4.6) and additional dense
models in the 7B–14B range.

\paragraph{Two benchmarks, both function-level.}
We do not evaluate class-level benchmarks (e.g., ClassEval) or
real-world projects with complex dependency graphs.

\paragraph{Pynguin time-budget.}
We compared our LLM methods against Pynguin with a 60-second search
budget per function. A budget of 300–600 seconds (recommended in
some Pynguin publications for harder functions) might close some
of the gap.

\subsection{Conclusion validity}\label{sec:limitations-conclusion}

\paragraph{Null results and statistical power.}
Our central method-level result is a null, so the relevant question
is whether we could have detected a real effect. With $n = 1{,}443$
observations across 16 cells and \texttt{sample\_idx} as a random
intercept, the mixed-effects model resolves a method contrast of
roughly 0.03 in mean kill rate at 80\% power. The largest observed
contrast is 0.011. We can therefore rule out a method effect of
practical size; we cannot rule out one smaller than about three
percentage points. A ceiling effect further limits resolution:
73.2\% of per-sample kill rates sit at exactly 1.0, so the metric
has little headroom on the three stronger models and the
discriminative variance is concentrated on llama3.2.

\paragraph{Sample sizes.}
The corpus is 100 source functions per cell, extended from the
30-function pilot whose results we reference in
\S\ref{sec:results-perbenchmark}. Cell sizes remain unbalanced after
the test filter (per-cell $n$ values are reported in
Table~\ref{tab:killrate-matrix} and Appendix~\ref{app:percell}),
ranging from $n = 50$ (Iterative Critique $\times$ llama3.2) to
$n = 100$. We mitigate this by reporting per-cell $n$ counts in
every results table, by treating \texttt{sample\_idx} as a random
intercept in the Mixed-LM analysis, and by repeating the central
analysis on the matched subset of 273 function-model units where all
four methods produced a valid suite for the same function on the
same model (\S\ref{sec:results-attrition}); the method spread there
is 0.011, against 0.016 on the full corpus.

\paragraph{Kill-rate $\times$ human-correctness correlation.}
A finding we reported in an earlier internal analysis—that mean
human\_correctness ratings correlate positively with mutation kill
rate (Pearson $r = +0.34$, $p = 0.04$) on two annotators
—disappeared when the third annotator's ratings were pooled in
($r = +0.18$, $p = 0.30$). We document the change in this
limitations section to be transparent about a result that was
preliminary and did not survive replication.

\section{Conclusion}\label{sec:conclusion}

We presented a mutation-testing-based empirical evaluation of four
LLMs-based unit-test generation methods across four open-weight
LLMs. The $4 \times 4$ matrix yielded 1{,}443 valid per-sample observations after filtering, drawn from a 100-function subset of HumanEval and MBPP. Five findings appear robust to the
limitations identified: (i) the mutation kill rate scales with LLM
capability and not with RAG-method choice, by a factor of 21.7;
(ii) method rankings do not generalize across LLMs, and no method
leads on more than two of the four; (iii) retrieval faithfulness is
a model-level rather than a method-level property, and its apparent
association with kill rate is confounded by model; (iv) three
independent annotators ranked Iterative Critique highest on all
three quality dimensions, contradicting the mutation-testing
result; (v) LLM-based test generation outperforms Pynguin's
SBST on overall mutation kill rate, but the gap concentrates on
the comparison and boundary operator families while Pynguin leads on
arithmetic and negate-boolean.

\paragraph{Future work.}
Three directions stand out as natural follow-ups. First, the
\emph{Pynguin--LLM hybrid} we sketched in
\S\ref{sec:discussion-sbst}—running Pynguin first for
coverage-driven assertions, then adding LLM-generated
comparison-operator oracles on uncovered branches
—should outperform either approach alone on the mutation-testing metric.
Second, \emph{closed-weight LLM replication}: our null on method
choice is established over a 3B--30B open-weight pool, and the
question of whether it persists where the model factor is less
dominant should be tested against GPT-4o, Claude Sonnet 4.6, and
Gemini 2.5.
Third, \emph{class-level and real-world benchmarks}: class-level
evaluation (ClassEval) and real-world project evaluation are
necessary to test whether the IC advantage transfers to code with
non-trivial state and side effects. A fourth methodological
direction concerns the \emph{human-evaluation rubric}: a future
replication should run a rubric-calibration session before
annotation and increase the rater pool to five or more.

\section{Hardware and inference configuration}\label{app:hardware}

All LLM-based test generation runs were executed on a single
NVIDIA A100 40\,GB GPU (Google Colab Pro+) for the four
open-weight models and on a CPU-only worker node for Pynguin
SBST. We list the exact knobs to support replication.

\begin{itemize}
\item \textbf{LLM runtime:} Ollama 0.3.x with the default
  \texttt{num\_ctx=4096}, \texttt{num\_thread=8},
  \texttt{num\_gpu=999} (offload all layers when possible).
\item \textbf{Open-weight models:} \texttt{llama3.2:latest} (3B,
  Q4\_K\_M), \texttt{phi4:14b} (14B, Q4\_K\_M),
  \texttt{qwen2.5-coder:9b} (called ``qwen3.5:9b'' in our
  results files for backward consistency with the autoresearch
  harness; 9B dense, Q4\_K\_M), and \texttt{qwen3-coder:30b}
  (30B MoE, Q4\_K\_M).
\item \textbf{Generation parameters:} temperature 0.2,
  \texttt{top\_p}=0.95, \texttt{top\_k}=40, repeat penalty 1.1,
  maximum 2048 generated tokens per call.
\item \textbf{RAG retriever:}
  \texttt{sentence-transformers/all-MiniLM-L6-v2} with cosine
  similarity over an in-memory NumPy index, $k = 5$ retrieval
  for Simple RAG and the first iteration of Iterative Critique
  RAG, and $k = 5$ uniform-random sampling for Random RAG.
\item \textbf{Iterative Critique loop:} maximum 3 iterations
  with an early-exit if the critic returns ``no issues''; both
  generator and critic share the same underlying model.
\item \textbf{Time budget:} 600\,s wall-clock per
  (method, model, sample); samples exceeding this budget are
  recorded as \emph{timeout} and excluded from per-cell means.
\item \textbf{Pynguin baseline:} Pynguin 0.45.0 with the
  DYNAMOSA algorithm, 60\,s budget per function, branch and
  line coverage as fitness signals, a mutation budget of 100,
  and a population size of 50 (all defaults). Generated tests
  were then fed through the same five-operator mutation pipeline
  used for the LLM methods.
\item \textbf{Mutation pipeline:} 5 AST-based operator families
  (arithmetic, boundary, comparison, negate\_bool,
  return\_none) applied per function, with a per function test
 filter that rejects generated tests failing on the
  \emph{original} (un-mutated) source.
\end{itemize}

\section{Method pseudocode}\label{app:pseudocode}

We summarize the four generation methods as compact
pseudocode. \texttt{LLM} denotes a single
\texttt{Ollama.chat} call, \texttt{retrieves} cosine-top-$k$ ($k=5$)
retrieval over the in-memory index, and \texttt{filters}
the original-source test filter.

\paragraph{Plain LLM.}
\begin{verbatim}
def plain_llm(function, signature, docstring):
    prompt   = TEMPLATE_PLAIN.format(function, signature, docstring)
    response = LLM(prompt)
    return filter(parse_tests(response), function)
\end{verbatim}

\paragraph{Random RAG.}
\begin{verbatim}
def random_rag(function, signature, docstring, corpus):
    chunks   = random.sample(corpus, k=5)
    prompt   = TEMPLATE_RAG.format(function, signature, docstring, chunks)
    response = LLM(prompt)
    return filter(parse_tests(response), function)
\end{verbatim}

\paragraph{Simple RAG.}
\begin{verbatim}
def simple_rag(function, signature, docstring, index):
    query    = QUERY_PREFIX + function[:300]
    chunks   = retrieve(index, query, k=5)       # cosine top-5
    prompt   = TEMPLATE_RAG.format(function, signature, docstring, chunks)
    response = LLM(prompt)
    return filter(parse_tests(response), function)
\end{verbatim}

\paragraph{Iterative Critique RAG.}
\begin{verbatim}
def iterative_critique(function, signature, docstring, index,
                       max_iters=3):
    chunks   = retrieve(index, QUERY_PREFIX + function[:300], k=5)
    draft    = LLM(TEMPLATE_GEN.format(function, signature,
                                       docstring, chunks))
    for _ in range(max_iters):
        critique = LLM(TEMPLATE_CRITIC.format(function, draft))
        if "no issues" in critique.lower():
            break
        draft = LLM(TEMPLATE_REFINE.format(function, draft, critique))
    return filter(parse_tests(draft), function)
\end{verbatim}

\section{Mutation operator definitions}\label{app:operators}

We use a five-family AST-based operator set chosen to align
with the canonical mutation-testing literature
\citep{just2014,andrews2005,papadakis2019survey}. Each operator is
applied as an in-place transformation of the function's
abstract syntax tree.

\paragraph{Arithmetic Operator Replacement (AOR).}
Replaces an arithmetic binary operator with each of the others
in the same family.
\begin{verbatim}
# Original
def f(a, b): return a + b
# Mutants
def f(a, b): return a - b
def f(a, b): return a * b
def f(a, b): return a / b
\end{verbatim}

\paragraph{Boundary Mutation (BND).}
Replaces an integer literal $n$ with $n \pm 1$, capturing the
``off-by-one'' defect family that dominates real-world
defects.
\begin{verbatim}
# Original
if i < 10:
# Mutants
if i < 9:
if i < 11:
\end{verbatim}

\paragraph{Comparison Operator Replacement (COR).}
Replaces a relational operator with each of the others in the
family $\{<, \le, >, \ge, ==, \ne\}$.
\begin{verbatim}
# Original
if x < y:
# Mutants
if x <= y:
if x > y:
if x == y:
\end{verbatim}

\paragraph{Negate Boolean (NEG).}
Inverts a boolean expression, including unary \texttt{not} and
boolean literal swaps.
\begin{verbatim}
# Original
if is_valid: return True
# Mutants
if not is_valid: return True
if is_valid: return False
\end{verbatim}

\paragraph{Return-None Replacement (RNR).}
Replaces the return expression of a function with
\texttt{None}, catching tests that rely solely on
\texttt{isinstance(...)}-style assertions but never inspect
the returned value.
\begin{verbatim}
# Original
def f(x): return x * 2
# Mutant
def f(x): return None
\end{verbatim}

\paragraph{Test filter.}
Before scoring the kill rate, every generated test suite is run
against the \emph{unmutated} source. Any test that fails on
the original is dropped from the suite. This avoids the
``false-positive kill'' confound, where a buggy test happens to
fail on a mutant by accident rather than by catching the
mutation.
